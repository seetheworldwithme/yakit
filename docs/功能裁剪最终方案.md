## 1. 判定原则

一个功能被判为「不需要展示」，需满足下列**任一**条件：

1. **超出需求范围**：`功能要求.csv` 无对应条目，且不属于已要求功能的必要支撑。
2. **攻击性 / 后渗透属性**：属维持访问、反弹 Shell、反序列化 payload 生成等，与「安全漏洞测试」的合规采购定位冲突（采购方为金融机构，非功能性要求第 26/27 条强调安全合规与国密）。
3. **数据外发合规风险**：需对接外部第三方平台，存在测试数据外泄风险。
4. **试验性 / 非生产**：beta 功能、运维调试工具、个人记录工具，不应在正式交付产品展示。

### 2.2 非功能性要求（25–31）—— 实现须保留，不一定展示入口

| 需求 | 能力 | 落地 |
| --- | --- | --- |
| 25 | 可靠性（多项目/多用户长时稳定） | 工程实现保留 |
| 26 | 安全检测/风险评估报告 | 供应商交付物 |
| 27 | 国密算法合规（SM 系列/AES/RSA） | `Codec` 国密实现保留 |

| 31 | 已知漏洞修复说明（含第三方组件） | 供应商交付物 |

> 结论：核心需求由 MITM、Web Fuzzer、History、PoC、批量执行、报告、风险、爆破、字典、数据对比、Codec、插件编辑器、插件仓库、项目管理、角色/用户管理、首页 共同覆盖。

## 3. 边界项 —— 虽未点名但应保留（必要支撑）

| 功能 | 路由 key | 保留理由 |
| --- | --- | --- |
| 字典管理 | `payload-manager` | 支撑需求 12「挂字典」 |
