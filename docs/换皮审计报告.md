## 一、结论先行

**判定：是换皮项目（高同质化风险，71.03 / 100）。**

`yakit-update-ui` 在结构、依赖、路由、状态管理、组件层级上与上游 `yakit` **几乎完全相同**，差异集中在视觉层（配色 / 字体 / 间距 / class 命名）。这与项目自身的既定目标一致——`CLAUDE.md` 明确「正将前端整体改写为 Sentinel，保留全部功能，仅改外观」，当前分支 `feat/sentinel-rebrand-layout` 即为此项工作。

**重要定性**：这是**同一仓库（`github.com/yaklang/yakit`）的授权衍生分支**，不是第三方抄袭。因此本报告的「建议」聚焦**工程治理**（降低双线维护成本、建立"皮 / 骨"分离边界），而非规避同质化争议。

## 二、评判标准（评分模型）

分析器对两棵源码树（自动跳过 `node_modules` / `dist` / `build` / `.git`）做四维度重叠度评分，加权合成总分。

### 2.1 加权公式

```
总分 = 骨架 × 0.40 + 布局 × 0.30 + 视觉 × 0.20 + 其它 × 0.10
```

每个维度为 0–100 的重叠度，越高 = 实现选择 / 代码越接近。

### 2.2 风险阈值

| 总分 | 风险 | 含义 |
| ---: | --- | --- |
| `< 30` | 低 | 相似可用同框架 / 通用模板 / 行业惯例解释 |
| `30–60` | 中 | 存在实质重叠，需人工复核架构、复用组件、核心流程 |
| `> 60` | 高 | 强换皮 / 克隆代码审计证据，需整改或提供来源证明 |

### 2.3 高危信号（任一命中即升高风险）

- 项目骨架核心重叠 **> 70**
- 页面布局组件结构重叠 **> 65**
- 多维度高分 + 业务逻辑 / API 集成同时匹配

### 2.4 四维度子指标构成

| 维度（权重） | 子指标 |

## 四、关键证据

### 4.1 同源铁证（版本控制 + 包身份）

| 项 | A: yakit-update-ui | B: yakit |
| --- | --- | --- |
| git origin | `github.com/yaklang/yakit.git` | `github.com/yaklang/yakit.git` |
| package.json `name` | `yakit` | `yakit` |
| package.json `version` | `1.4.7-0626` | `1.4.7-0630` |
| 当前分支 | `feat/sentinel-rebrand-layout` | `master` |

二者来自**同一远端仓库、同一包名、同一版本代**，A 是 B 的换皮工作分支。

### 4.2 依赖与版本逐字相同（依赖版本重叠 100）

抽样的 20 项依赖全部 `exact` 匹配，包括核心栈：

- `electron` `27.0.0`、`electron-builder` `26.15.3`、`electron-updater` `^4.3.9`
- `@grpc/grpc-js` `^1.3.6`、`@grpc/proto-loader` `^0.6.4`
- `axios` `0.26.1`、`dompurify` `^3.0.5`、`chrome-launcher` `^0.15.0`
- `concurrently` `^6.2.0`、`cross-spawn` `^7.0.6`、`env-cmd` `^10.1.0`

→ 引擎、构建链、gRPC 通道、网络层一字不差。

### 4.3 组件层级 100% 重叠

入口与骨架文件完全对应、结构签名一致：

- `app/renderer/src/main/src/index.tsx`
- `app/renderer/src/main/src/NewApp.tsx` / `ChildNewApp.tsx`
- `app/renderer/src/main/src/auxWindow/AuxWindowApp.tsx` / `aux-entry.tsx`
- `app/renderer/src/main/src/auxWindow/components/AuxXterm/AuxXterm.tsx`
- `app/renderer/src/main/public/index.html` / `yakit-aux.html`

→ 渲染进程入口、辅助窗口、xterm 终端组件等**整棵组件树原样保留**。

### 4.4 视觉层正在被替换（换皮的"皮"）

- 配色重叠 55.67、字体 51.33、间距 39.84、**动效仅 13.63** —— 换皮分支已显著偏离原视觉。
- 但 **token 命名重叠 75.90** —— token 体系（`--Colors-Use-*` 等变量名）仍沿用原命名空间，只是值改了。
- **页面 class 命名重叠仅 17.51、响应式仅 6.48** —— 大量 class 名被重写、响应式断点逻辑被改造（如 MITM 被动插件「纵向侧栏改横向」等近期 commit 即属此类）。

### 4.5 业务逻辑保留（"只动 UI 不动逻辑"实证）

- 第三方服务（axios / fetch / firebase / graphql / gtag / sentry）配置重叠偏低（23.58），但这是分析器层面；实际业务逻辑 token 重叠 49.24、API 端点重叠 38.75。
- 共享组件实现重叠 84.63、布局工具模式 95.36 —— 组件实现与布局工具函数（间距/栅格等）几乎原样复用。

| 维度 | 现象 | 含义 |
| --- | --- | --- |
| 骨架 95.73 | 依赖/构建/状态管理/工程配置几乎全同 | 上游 rebase 成本极低（好事）；但也意味着换皮分支**没有任何架构层面的独立性** |

| 视觉 47.14 | 配色/字体/间距/动效已分歧，token 名仍沿用 | 半成品换皮：值在改，token 命名体系尚未独立 |

**一句话**：**骨头（骨架 + 组件树）原样保留，皮（视觉值 + class 名）换了一半。** 这是典型的"样式层换皮"，而非架构层重构。

## 六、建议（工程治理导向）

> 因本项目为**授权品牌重塑**（同仓库分支），建议目标不是"降低相似度分数"，而是：**让换皮层与核心层解耦，使上游 `yakit` 能持续 rebase 进来，同时换皮改动不污染核心、不制造合并地狱。**

### 6.1 已经做对的方向（继续坚持）

- ✅ 颜色统一走 token：`sentinelTheme.ts` 集中定义 114 个 `--Colors-Use-*`，组件 / scss 不硬编码 `#hex`。
- ✅ 主题注入走 `applyYakitThemeColors`，启动时注入 `documentElement`。
- ✅ "只动 UI 不动逻辑"约定，保留 state / 接口 / 路由。

### 6.2 建议补强（按优先级）

**P0 — 建立"皮 / 骨"分离边界（降低 rebase 痛苦）**
- 把 Sentinel 换皮的**所有**改动收敛到可识别的边界：`sentinelTheme.ts` + 同名 `.scss` 的 `:global`/自定义类覆盖层 + 少量形态塑形文件。
- 核心 JSX / 业务组件尽量**不改源文件**，改样式只动 `.scss`；必须改 JSX 时（如布局重排）集中在已知的共享文件（`Home.tsx` / `newRoute.tsx` / `MainOperatorContent.tsx`）并加注释标注"Sentinel 换皮改动"。
- 目标：上游一次 rebase，冲突只落在少数已知文件，而非遍地开花。

**P1 — 让 token 体系可独立演化（视觉维度）**
- 当前 token 命名重叠 75.90（仍沿用 `--Colors-Use-*` 命名空间）。若希望 Sentinel 视觉真正自成体系，可在保留兼容映射的同时，建立 Sentinel 自有命名层（如 `--Sentinel-Bg-*` / `--Sentinel-Accent-*`），旧名作别名指向新名。
- 补齐动效规则（当前重叠仅 13.63，说明已大量改写——顺势沉淀一套 Sentinel motion token，避免散落各 `.scss`）。

**P2 — 组件塑形层显式化（布局维度）**
- 组件层级 100% 重叠本身**不是问题**（这是换皮的必要前提）。但为降低维护耦合，可把"圆角 / 阴影 / 间距 / 字号"等形态塑形集中在 yakitUI 组件库的样式覆盖层，而非散落各页面。
- 避免为"降分"而做无意义重命名/包装（脚本明确：cosmetic churn 是 poor remediation）。

**P3 — 双线漂移治理**
- 保持 `yakit-update-ui` 的换皮改动以**可 cherry-pick / 可 rebase** 的粒度提交（小步、单一关注点），便于定期同步上游 `master`。
- 维护一份「换皮改动清单」（哪些文件 / 哪些 token / 哪些组件被改），作为 rebase 冲突预警地图。

### 6.3 不建议做的事

- ❌ 为降低 71 分而重写路由 / 状态管理 / 目录结构 —— 上游同步价值远高于分数，且 CLAUDE.md 已明确"保留全部功能"。
- ❌ 把组件树推倒重建 —— 会断掉与上游的 rebase 通道，得不偿失。
- ❌ 在组件 / scss 里硬编码颜色去"看起来不一样" —— 违反 token 规范，且无法集中维护。

## 七、方法说明与局限

- 评分基于源码树静态分析（依赖、目录、路由、JSX 标签序列、CSS 值/token、函数名/端点字符串等），**不含运行时行为对比**。
- 已自动忽略 `node_modules` / `dist` / `build` / `.git` 等生成物；lockfile 噪声未计入依赖身份判断。
- 框架默认（CRA / Electron 27 / antd 4）会产生一部分"合理重叠"，但本项目骨架 95.73 远超框架默认能解释的范围，且有同源 git 证据佐证。
- 默认权重：骨架 40 / 布局 30 / 视觉 20 / 其它 10。如调整阈值/权重，分数不再适用默认标准。
