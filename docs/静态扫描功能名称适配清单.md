# IRify 静态代码扫描功能名称适配清单（审校修订版）

> 审核对象：仓库根目录《静态代码扫描功能清单.md》、IRify 当前前端源码、原适配清单。
>
> 审核基线：`feat/irify-debrand`，`f33f71ccf`，2026-08-28。
>
> 本文仅给出名称与布局改造方案，尚未修改业务代码。
>
> 路径缩写：`SRC` = `app/renderer/src/main/src`，`LINK` = `app/renderer/engine-link-startup/src`。

## 一、审核结论

原适配清单的方向是对的：应把任务书中的原型名称放到首页显眼位置，并让 IRify 的页面命名更贴近静态代码扫描。但原方案不能直接实施，需要先修正以下问题：

1. **不应把产品名从“系统”全局改成“原型”**。
   - 当前去品牌化项目已经把产品名确定为“智能化代码安全检测与验证系统”，并用于窗口标题、启动页和应用元信息。
   - “智能化代码安全检测与验证原型”是任务书及第三方测试报告的验收名称，适合在首页主视觉区明确展示，不应替换整个产品品牌名。
   - 因此不修改两个 `getReleaseEditionName()`，也不新增 `versionFetchers` 的“原型”键。
2. **不能把研究方法名直接当作操作菜单名**。
   - “结构化提示模板驱动大模型推理”“代码语义相似度评估与路径可达性验证”等是方法或能力名称，不是用户任务名称。
   - 这些长名称放进顶部菜单或四列功能卡，会降低可理解性，并存在明显换行、挤压风险。
3. **原文对菜单名称中枢的判断不完整**。
   - `YakitRouteToPageInfo.label` 会影响内部 `menuName` 和页签名，但社区版展开菜单的二级文案在 `MenuMode.tsx` 中直接渲染旧 i18n key；只改 `label` 不会同步更新。
   - 企业版二级菜单优先渲染 `labelUi`；只改 `label` 同样不会更新可见名称。
4. **部分功能映射超过了现有代码能够证明的能力边界**。
   - “规则管理”当前管理的是 SyntaxFlow 规则、规则组、语言、调试和上传下载，把它直接命名为“漏洞特征库”会暗示已经实现形式化漏洞特征描述语言及特征数据模型，前端代码不足以证明这一点。
   - “AI Skill 安全分析”会切换到后端 `ai_skill_audit` focus mode，它不是“领域知识增强的模型微调”。把两者直接等同属于功能错配。
   - “代码扫描”页面是按规则组/关键词选择规则、执行任务并查看结果的扫描工作台，直接改为“全链路漏洞挖掘”范围过大。
5. **语言与指标只能按已验证能力展示**。
   - 前端规则语言列表明确包含 Java、PHP、JavaScript，同时还包含 Yaklang、Golang 和通用规则；但项目编译语言由后端插件参数动态提供。
   - “百万行 ≤5 分钟”“准确率 ≥90%”“自动化利用成功率 ≥85%”是验收指标，不是当前首页统计数据，不能仅靠改文案伪装成已实现指标。

结论：**保留原型名上首页的目标；重做菜单映射；研究方法名放在说明/能力区；所有未由引擎或测试证明的能力标为待确认。**

## 三、命名原则

名称分成三层，不混用：

1. **产品名**：智能化代码安全检测与验证系统。用于窗口、启动页、应用元信息，保持不变。
2. **验收原型名**：智能化代码安全检测与验证原型。首页首屏精确展示，文字不得缩写或改写。
3. **用户功能名**：使用短、可操作的任务名称；任务书中的方法名作为副标题、能力说明或验收口径，不直接塞入菜单。

同时遵守以下边界：

- 页面做什么就叫什么，不用文案覆盖尚未实现的能力。
- 菜单建议控制在 2–8 个汉字；完整方法名放到页面说明区。
- 同一路由在一级菜单、二级菜单、首页卡片、快速入口、页签和页面标题中使用同一套短名。
- 指标文案必须有实际测量数据来源；没有数据时只写“验收目标”，不能写成当前成绩。

## 四、最终推荐命名

### 4.1 顶部菜单与页签

| 现名 | 推荐名 | 处理结论 | 对应任务书口径 |
|---|---|---|---|
| 一级：代码审计 | **静态代码扫描** | 修改 | 静态分析与漏洞挖掘的产品主流程 |
| 项目管理 | **扫描项目** | 修改 | Java/JavaScript/PHP 项目输入与编译管理 |
| 代码审计 | **静态分析** | 修改 | 顶部菜单/页签空间有限；页面标题与首页卡片可使用“静态分析工作台” |
| AI代码审计 | **智能辅助审计** | 修改 | 大模型辅助推理；完整方法名放页面说明，不放菜单 |
| 代码扫描 | **扫描任务** | 修改 | 规则选择、扫描执行、任务与结果查看 |
| 规则管理 | **检测规则** | 修改 | 当前实际是 SyntaxFlow 检测规则管理；不直接宣称为漏洞特征库 |
| 审计漏洞 | **漏洞结果** | 修改 | 扫描/审计发现结果、定位与详情 |
| Java 反编译 | **Java 反编译** | 保留 | Java 输入的辅助处理能力，不强行映射为独立研究方法 |
| 一级：数据库 | **报告中心** | 修改 | 该一级下目前只有“报告”，原名“数据库”不能表达用户任务 |
| 报告 | **检测报告** | 修改 | 原型验证、扫描结果交付的报告承载入口 |

不采用原方案中的以下名称：

- 不用“静态分析引擎”直接代替菜单名：它是系统模块/能力名；菜单/页签使用“静态分析”，页面标题与首页卡片使用“静态分析工作台”。
- 不用“大模型推理审计”：现有前端能确认 AI 审计，但不能仅凭前端确认其完整实现“结构化提示模板驱动大模型推理”。
- 不用“全链路漏洞挖掘”代替扫描任务：该名称覆盖编译、分析、验证等完整链路，超出单个扫描页职责。
- 不用“漏洞特征库”直接代替规则管理：只有在引擎和数据模型确认支持任务书中的形式化漏洞特征描述后才能升级为此名。
- 不用“领域知识增强安全分析”代替 AI Skill 安全分析：两者不是同一功能。

### 4.2 首页首屏

首页 Hero 是原型名称最显眼、最稳定的展示位置。推荐：

| 位置 | 现值 | 推荐值 |
|---|---|---|
| H1 `IRifyHome.pageTitle` | 代码审计工作台 | **智能化代码安全检测与验证原型** |
| 副标题 `IRifyHome.pageSubtitle` | 区分 AI 联网审计与 SSA 离线规则审计，统一查看扫描成果与风险态势 | **面向电力业务程序的静态代码扫描、漏洞定位与智能辅助验证** |
| 可选补充标签 | 无 | **课题：电力业务程序语义重构与静态符号验证协同漏洞挖掘技术** |

产品名“智能化代码安全检测与验证系统”继续保留在窗口标题和启动页，首页 H1 展示验收原型名。这样既不破坏现有产品命名，也能满足原型名称显眼、可截图、可验收的要求。

布局调整要求：

- `page-header` 增加适当的响应式换行或在较窄宽度下让统计卡换到下一行。
- H1 保持完整原型名，不使用省略号；窄窗口允许整体 Hero 增高。
- 不建议把课题全名与 Java/JavaScript/PHP 说明全部塞入同一行副标题。

静态扫描是产品主线，建议把离线静态分析能力排在前面，AI 能力作为辅助验证。调序时还要同步交换卡片的主次视觉样式：静态分析与扫描任务使用深绿主卡，两个 AI 入口降为浅色辅助卡。

## 五、任务书明确名称如何落位

任务书名称应进入“能力说明/验收口径”，而不是全部变成导航项：

| 任务书明确名称 | 推荐展示位置 | 状态要求 |
|---|---|---|
| 智能化代码安全检测与验证原型 | 首页 Hero H1 | 直接展示，P0 |
| 电力业务程序语义重构与静态符号验证协同漏洞挖掘技术 | 首页 Hero 可选课题标签、关于/版本信息页 | 直接展示，避免塞进菜单 |
| 静态分析引擎 | “静态分析工作台”页面说明 | 可展示；前端已有 SSA/规则审计链路 |
| 上下文敏感信息识别 | 静态分析工作台能力标签 | 需引擎负责人确认具体实现 |
| SSA IR 语法树映射、静态单变量赋值分析 | 项目编译/静态分析说明 | 前端存在 SSA 项目编译，但完整算法口径需引擎确认 |
| 跨语言语法树映射规则集（Java/JS/PHP） | 检测规则或静态分析页的支持能力说明 | 规则语言包含三者；“跨语言映射规则集”仍需引擎确认 |
| “漏洞特征-攻击模式-环境约束”三元组表征 | 智能辅助审计页面的能力说明 | 未在本次前端审查中找到直接证据，暂不对外展示 |
| 结构化提示模板驱动大模型推理 | 智能辅助审计页面说明 | 前端仅能确认 focus mode 和 AI 会话，提示模板实现需后端确认 |
| 代码语义相似度评估与路径可达性验证 | 漏洞结果详情或智能验证说明 | 未在本次前端审查中找到直接证据，暂不对外展示 |
| Java、JavaScript、PHP | 首页支持语言区、项目创建/规则筛选 | 在项目编译和实际扫描通过三语言验证后再作为“已支持”展示 |
| 百万行 ≤5 分钟、准确率 ≥90%、自动化利用成功率 ≥85% | 独立“验收指标”区域或验证报告 | 必须有测试数据；不得混入当前统计卡 |

研究内容 3 的“漏洞利用代码生成”和“自动化漏洞利用成功率”不应通过改名塞入当前 IRify 静态扫描菜单；如果后续确有功能，应新增明确的验证/利用流程并单独验收。

## 六、代码改动落点

### P0：原型名称上首页

1. 修改 `SRC/locales/{zh,en,zh-TW}/irifyHome.json` 的 `IRifyHome.pageTitle` 与 `pageSubtitle`。
2. 如增加课题标签，在 `SRC/pages/irifyHome/IRifyHome.tsx:185-189` 增加专属元素，并在 `IRifyHome.module.scss` 添加样式。

   - 两个主进程 `yaklangAndYakit.js` 的 `versionFetchers`。

### P1：统一菜单、页签与首页短名

1. 在 `SRC/routes/newRoute.tsx` 的 IRify 一级菜单分支修改一级 `label/labelUi`。

5. 同步首页 `irifyHome.json`、AI 审计页 `irifyAiCodeAudit.json`、近期项目表操作文案。

### P2：方法名称与验收能力区

1. 由引擎/算法负责人确认第五节各项“待确认”能力。
2. 只把已确认的能力加入首页说明、工作台帮助区或关于页。
3. 量化指标接入真实测试或统计数据后，再增加指标展示；否则只在验收材料中作为目标出现。

## 七、原适配清单逐项裁定

| 原建议 | 裁定 | 修订意见 |
|---|---|---|
